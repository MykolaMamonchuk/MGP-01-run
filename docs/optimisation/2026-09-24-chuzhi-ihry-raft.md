# Розбір збірки: «виживання на плоту» (Mega Play Games)

Дата: 2026-09-24. Пакет
`com.mega_play_games.ocean.raft.shark.craft.survival_games.crafting.building.last_day.survive.fishing.hungry`,
встановлений на Redmi 8A. Розбирали лише файли збірки (`adb shell pm path` + `adb pull`);
гру не запускали, кадр не міряли — це окремий захід.

Навіщо: у нас (`2026-09-23-final-report.md`) уся ціна кадру — робота піксельного шейдера.
Ця гра — океан на весь екран на тому самому залізі. Цікавить «якою ціною».

---

## 1. Рушій

| Що | Значення |
|---|---|
| Рушій | **Unity 6000.0.64f1** (Unity 6 LTS) |
| Скриптинг | IL2CPP (`libil2cpp.so`) |
| ABI | **лише `armeabi-v7a`** — 32-бітна збірка, 64-бітної немає |
| Конвеєр | **Built-in Render Pipeline**, не URP (`m_CustomRenderPipeline` = 0) |
| Шлях рендеру | Forward (`renderingPath` = 1) на всіх трьох tier'ах |
| API | GLES3 (`#version 300 es`) + Vulkan (shaderPlatform 9 і 18) |
| Інше | Swappy (`libswappywrapper.so`) для темпу кадрів, FMOD для звуку |

### Ключові налаштування якості

За замовчуванням увімкнено рівень **«Fastest»** (`m_CurrentQuality` = 0):

- `pixelLightCount` = **0** — жодного попіксельного світла. Усі 178 точкових світел у
  сцені працюють лише як вершинні/SH.
- `shadows` = 2, але при `pixelLightCount` = 0 тіні фактично нікому кидати;
  `shadowDistance` = 15 м, каскадів немає на жодному tier'і (`useCascadedShadowMaps` = false).
- `globalTextureMipmapLimit` = **1** — усі текстури втрачають верхній мип у пам'яті.
  256×256 працює як 128×128. Це безкоштовна половина пропускної здатності.
- `antiAliasing` = 2, але **всі камери мають `m_AllowMSAA` = false** → MSAA вимкнено.
- HDR вимкнено скрізь (`useHDR` = false, `m_HDR` = false на кожній камері).
- Streaming mipmaps увімкнено, бюджет 512 МБ.
- Камери: far = 3000 м, `m_ClearFlags` = 2 (суцільний колір, **не skybox**),
  occlusion culling здебільшого вимкнено.
- Пост-обробки немає. Шейдери `Hidden/Kino/Fog`, `Hidden/Kino/Obscurance` (SSAO)
  у збірці лежать, але **жодного матеріалу на них немає** — не використовуються.

## 2. Розмір збірки та як пакують ресурси

| Файл | Розмір |
|---|---|
| `base.apk` | 112 МБ |
| `split_UnityDataAssetPack.apk` | 62 МБ |
| `split_AddressablesAssetPack.apk` | 47 МБ |
| `split_config.armeabi_v7a.apk` | 40 МБ |
| **Разом** | **≈261 МБ** |

Пакування — Play Asset Delivery + Addressables. Усі ресурси лежать у **восьми
файлах-контейнерах**, не в тисячах окремих:

- `assets/bin/Data/data.unity3d` (base) — основна сцена, UI, персонажі
- `assets/bin/Data/datapack.unity3d` (23,5 МБ) — світ, предмети, океан
- `assets/aa/Android/*.bundle` — 6 бандлів Addressables:
  `preloadable_assets_all` (28,3 МБ), `mobile_buildings` (12,9 МБ),
  `mobile_hand_props` (5,7 МБ), `mobile_props` (1,0 МБ) + два службові
- `assets/aa/catalog.bin`, `CustomAssetPacksData.json` — каталог Addressables

Тобто поділ не «за текою», а **за моментом потреби**: те, що треба одразу — у
`data.unity3d`; косметика персонажів — у `preloadable`; будівлі та реквізит — окремими
бандлами, що завантажуються за потреби.

## 4. Карти нормалей — є, і багато

Це головна несподіванка.

- **203 унікальні карти нормалей**, 311 об'єктів у збірці.
- **544 з 717 матеріалів (76%) мають прив'язаний `_BumpMap`/`_NormalsTex`.**
- Формати: ASTC_6x6 — 273, ETC2_RGB — 17, ASTC_8x8 — 12.
- Розміри: 256×256 — 177, 128×128 — 61, 512×512 — 43.

Основний шейдер світу — `Mobile/Bumped DiffuseX` (366 матеріалів), тобто мобільний
дифузний **із картою нормалей**. Далі `MeGaMe/PBR_GLES_20_RAFT` (49 матеріалів) —
власний PBR з упакованими текстурами: `_MainTex` = Albedo(RGB) + Metallic(A),
`_NormalsTex` = Normals(RGB) + Smoothness(A). Дві вибірки на матеріал замість чотирьох.

Але — і це важливо — **на воді, небі, сонці та відблиску сонця карт нормалей немає взагалі**.
Вони стоять там, де об'єкт малий на екрані (реквізит, одяг, будівлі), і їх немає там, де
поверхня займає пів екрана.

## 6. Як зроблена вода — головне

Один меш, один матеріал, один шейдер, **одна текстура**.

### Меш

`OceanPlane` — **2652 вершини, 5100 трикутників**. Одна площина. Не тесельована сітка,
не Clipmap, не LOD-кільця.

### Матеріал

Матеріал `Water`, шейдер `Unlit/Water`. Прив'язана рівно одна текстура:

```
_MainTex = ColorNoise, 256×256, ETC2_RGBA8, tiling 0.25
_FluctuationAnimationSpeed = 0.5
_FluctuationSpeed          = 0.05
_Offset                    = 0.01
_WaveHeight                = 0.2
_WaveSpeed                 = 2.0
_TransparentColor          = (0.008, 0.178, 0.335, 0.959)
_Color1 / _Color2, _HighGradientColor / _LowGradientColor — градієнт дня й ночі
```

Та сама `ColorNoise` 256×256 обслуговує ще й **небо** (`Unlit/SkyDome`) і **відблиск
сонця** (`Unlit/SunReflection`). Тобто на весь океан, все небо й усі блики — **одна
текстура 256×256, тобто 87 КБ**.

Черга — Transparent, **ZWrite Off**, змішування увімкнено.

### Вершинний шейдер (витяг з GLES3-блоба)

```glsl
u_xlat9 = _IOTimeWater * 4.0 + worldPos.x;
u_xlat9 = sin(u_xlat9);
u_xlat9 = u_xlat9 * _WaveHeightMultiplyer;
u_xlat0.y = u_xlat9 * 0.2;          // хвиля лише по Y, лише від worldPos.x
...
vs_TEXCOORD3 = clipPos.z * unity_FogParams.z + unity_FogParams.w;   // ТУМАН — ПОВЕРШИННО
```

**Один синус** на вершину. Хвиля — плоска біжуча, залежить тільки від світової X.
Плюс два набори UV: один у світових координатах (`worldPos.xz * _MainTex_ST`), другий
зсунутий на позицію камери з коефіцієнтом `_Offset / (camY - worldY)` — дешева підробка
паралаксу до горизонту.

### Піксельний шейдер — цілком

```glsl
uniform mediump vec4 _HighGradientColor, _LowGradientColor, _TransparentColor, unity_FogColor;
UNITY_LOCATION(0) uniform mediump sampler2D _MainTex;

void main() {
    u_xlat0.xy  = vs_TEXCOORD0.zz + vs_TEXCOORD0.xy;
    u_xlat16_0  = texture(_MainTex, u_xlat0.xy);      // вибірка 1
    u_xlat1.xy  = vs_TEXCOORD0.zz + vs_TEXCOORD1.xy;
    u_xlat16_1  = texture(_MainTex, u_xlat1.xy);      // вибірка 2 (та сама текстура)
    u_xlat0     = u_xlat16_0 - u_xlat16_1;
    u_xlat0.x   = dot(vs_TEXCOORD2, u_xlat0);         // 4 анімовані фази з вершинного
    u_xlat16_2  = max(1.0 - abs(vs_TEXCOORD1.z), 0.0);
    u_xlat16_2  = u_xlat16_2 * u_xlat16_2;
    u_xlat16_2  = 1.0 - u_xlat16_2 * u_xlat16_2;      // псевдо-френель
    u_xlat0.x   = clamp(u_xlat0.x + u_xlat16_2, 0.0, 1.0);
    u_xlat16_2  = (u_xlat0.x * u_xlat0.x + u_xlat0.x) * 0.5;
    u_xlat16_6.xyz = _LowGradientColor.xyz - _HighGradientColor.xyz;
    u_xlat16_1.xyz = u_xlat16_2 * u_xlat16_6.xyz + _HighGradientColor.xyz;
    u_xlat16_1.w   = 1.0;
    u_xlat16_0  = u_xlat0.xxxx * (u_xlat16_1 - _TransparentColor) + _TransparentColor;
    // туман — одна інтерполяція з готовим коефіцієнтом із вершинного шейдера
    SV_Target0.xyz = clamp(vs_TEXCOORD3,0.0,1.0) * (u_xlat16_0.xyz - unity_FogColor.xyz)
                     + unity_FogColor.xyz;
    SV_Target0.w   = u_xlat16_0.w;
}
```

Порахуймо, що цього **немає**:

- немає карти нормалей
- немає DEPTH_TEXTURE, немає soft-edge / глибини води
- немає SCREEN_TEXTURE, немає заломлення
- немає відбиття (ні планарного, ні кубомапи, ні SSR)
- немає освітлення взагалі — шейдер `Unlit`
- немає піни по краю
- немає процедурного шуму в пікселі

Є: **2 вибірки з однієї текстури 256×256 і близько 25 ALU, з них половина — mediump**.
Уся анімація живе у вершинному шейдері й приходить у фрагмент готовими інтерполянтами
(`vs_TEXCOORD2` — чотири фази, `vs_TEXCOORD3` — коефіцієнт туману).

### Туман

RenderSettings: **Linear, від 15 до 50 м**, при far камери 3000 м. Коефіцієнт рахується
**у вершинному шейдері** одним `madd`, у фрагменті — один `lerp`. Це рівно те, що ми
зробили в себе як «дешеву апроксимацію».

### Небо

Не skybox. Камери чистяться суцільним кольором (`m_ClearFlags` = 2), а небо — це **меш
купола** з шейдером `Unlit/SkyDome`: та сама `ColorNoise` (tiling 2, зсув −1.42) плюс
`NightSky` 512×512 ETC2_RGB для зірок. День/ніч — інтерполяція між
`_HighGradientColor` і `_LowGradientColor`; хмарність — чотири фази
`fract(_IOTime*0.1 + {0,0.25,0.5,0.75})`, згорнуті в трикутну хвилю, **теж у вершинному
шейдері**.

### Блики й бризки

`Unlit/SunReflection` — окремий квад у черзі Overlay, текстури `SUN` (128×128 RGBA32) +
`ColorNoise`. Бризки — партикли `g51/WaterSplash_DayAndNight`.
Прапори й ганчірки на плоту — `DirectLit/Wave Object`: хвилю по вітру теж рахує
вершинний шейдер (`_WindSpeed`, `_WindForce`, `_MaskUV`).

## 7. Що з цього варто взяти нам

### Брати

**1. Вода = запечена текстура + вершинна хвиля. Ми вже це зробили, тепер знаємо, що не
перестаралися.** Ми замінили процедурний шейдер води запеченою текстурою і виграли 94 мс.
Ця гра — комерційний океан на весь екран на такому самому залізі — робить рівно те саме,
і навіть скромніше: дві вибірки з однієї текстури 256×256. Наш напрямок правильний,
відкочувати нема чого.

**2. Одна текстура на воду, небо й блики.** У них `ColorNoise` 256×256 обслуговує три
різні поверхні через різний tiling і різні кольори-уніформи. 87 КБ на все. Нам варто
перевірити, чи можна нашу запечену воду переюзати десь ще (небо, туман, блики) замість
окремих файлів.

**3. Уся анімація — у вершинному шейдері, у фрагмент приходять готові інтерполянти.**
Чотири фази анімації хмар і коефіцієнт туману вони рахують на вершину й передають через
`TEXCOORD`. При 2652 вершинах на океан проти мільйона пікселів це майже безкоштовно.
Наше правило «ціна — це піксельний шейдер» тут доведене до кінця: у фрагменті не
залишилося нічого, що можна було винести.

**4. Туман — лінійний, коефіцієнт у вершинному, у фрагменті один lerp.** Підтверджує нашу
заміну. Дистанції в них 15–50 м при far 3000 — тобто туман працює ще й як прихована
відсічка дальності.

**5. Ноль попіксельних світел.** `pixelLightCount` = 0 на рівні за замовчуванням. Тобто
комерційна гра з 178 точковими світлами в сцені не рахує **жодного** з них попіксельно.
Тіні при цьому формально «увімкнені», але кидати їх нікому. Наше «тіні геть» — це
не екстремізм, це галузева норма для цього класу пристроїв.

**6. Мип-ліміт замість зменшення вихідних текстур.** `globalTextureMipmapLimit` = 1 на
профілі «Fastest» ріже всі текстури вдвічі в пам'яті, не чіпаючи файли. У Godot аналог —
`rendering/textures/default_filters/texture_mipmap_bias` та імпортні налаштування; варто
подивитися, чи можна зробити це одним перемикачем профілю замість 137 переімпортів.

**7. Один матеріал на об'єкт.** Медіана 1, максимум 2 на 3002 рендерери. Просте правило,
яке варто взяти як інваріант і перевіряти тестом.

### Не брати

**1. Не повертати карти нормалей на великі поверхні.** Так, у них 76% матеріалів із
нормалями — але це одяг, реквізит і будівлі, тобто дрібні об'єкти на екрані. **На воді,
небі, сонці й відблисках нормалей немає жодної.** Наш виграш 18% на декорі був там, де
об'єкти дрібні й нормаль усе одно не видно — це інший випадок, ніж у них. Висновок:
їхній приклад **не** є аргументом повертати нормалі; він є аргументом, що нормалі мають
право жити на дрібному декорі, якщо ми колись захочемо кращий вигляд і матимемо запас.
Поки запасу немає — рішення не переглядати.

**2. Не гнатися за кількістю текстур.** У них 1050 унікальних текстур проти наших 137, і
це працює — бо на рендерер один матеріал, а розмір 256×256. Отже, **наша проблема не в
кількості файлів**, і цілитися в «одну текстуру на все», як у Subway Surfers, не
обов'язково. Головне — розмір і кількість вибірок у шейдері, а не кількість файлів.

**3. Не брати ASTC/ETC2-мішанину.** У них формати розкидані безсистемно (896 ASTC, 499
ETC2, 109 взагалі без стиснення, 93 з них RGBA32). Це просто безлад, а не оптимізація.
Нам варто мати одне правило й тест, що його перевіряє.

**4. Не брати 261 МБ і 32-бітну збірку.** Розмір у них — плата за косметику й рекламні
SDK, не за графіку. 32-бітний ABI без 64-бітного — це вже не відповідає вимогам Play і
нам не приклад.

**5. Не брати плоский `OceanPlane` без LOD як готове рішення.** 2652 вершини на весь
океан їм вистачає, бо камера низько над водою і туман ріже все за 50 м. Якщо в нас
камера дивиться далі — та сама геометрія дасть помітні сходинки на хвилях.

### Що лишилося невідомим

- **Скільки це коштує в мілісекундах** — ми не запускали гру. Числа кадру — окремий захід.
- **Чи справді малюється другий прохід обведення** (`_outline_Mobile`, 226 мешів). У
  бандлах немає сцени, з якої видно, як їх вмикають; це може бути і другий прохід, і
  просто мобільний варіант експорту.
- **Скільки об'єктів реально в кадрі** — статичний розбір дає лише вміст бандлів, не
  склад сцени в конкретний момент.
- **Чи вмикає гра «Good»/«Fantastic» на потужніших пристроях у рантаймі** — код IL2CPP
  ми не декомпілювали.
